# Operations internals

Developer reference for persistence, filesystem safety, recovery, and runtime behavior. For everyday use, see the [operations guide](../operations.md).

## Filesystem and container permissions

The image defaults to UID/GID `1000:1000`. The Compose examples select the runtime identity from host-side interpolation variables:

```dotenv
PUID=1000
PGID=1000
TZ=Europe/Zagreb
```

Compose resolves `PUID` and `PGID` before the container starts and applies them to both `user:` and `/tmp` tmpfs ownership. Put them in the project's `.env` file or export them in the invoking shell. Adding them only to the service's `environment:` mapping would not change the process identity. `TZ` is passed into the container, whose image includes timezone data.

The selected identity expects:

- `/config/config.yaml`: readable configuration, normally a read-only mount.
- `/data`: writable SQLite database, LAPSE speech cache, pack cache, and process lock.
- Every configured media root: readable for probing/hashing and writable for atomic sidecar installation.
- `/tmp`: writable ephemeral space; the Compose examples provide a bounded tmpfs.

Create host directories before starting and grant the selected UID/GID access. The container remains rootless and does not create users or change ownership at startup. The mounted paths and optional `install.uid`/`install.gid` must agree. Chown is omitted unless those optional settings are configured; unprivileged containers normally leave them unset.

`install.file_mode` defaults to `0644`, accepts an octal non-executable mode, and is applied before atomic publication:

```yaml
install:
  file_mode: "0640"
  # uid: 1000
  # gid: 1000
```


### Unreadable media

`workflow.MediaUnavailableError` marks a search that failed because its media file itself could not be found or read (`ENOENT`, or a mount failure from `domain.MountUnavailable`: `ENOTCONN`, `EIO`, `ESTALE`, `EHOSTDOWN`, `EHOSTUNREACH`, `ETIMEDOUT`, `ENODEV`, `ENXIO`). `checkMediaAvailable` returns it directly; an ffprobe run that does not finish within 5 minutes (`inventory.ErrProbeTimedOut`, a hung mount) is marked too, and the probe is awaited only until then, since a process blocked in a FUSE read cannot be killed. Such a timed-out run is tracked until its process returns: while one is still blocked for a media path, probing that path returns `ErrProbeTimedOut` at once without starting another ffprobe, and while four are blocked on one mount (`maxStuckProbes`) no new probe starts on that mount, so a long outage cannot pile up processes, while probes of other mounts still run. The mount is the longest configured media root containing the path plus the next directory below it (`/media` + `tv` is `/media/tv`, since one root often holds several network mounts; a file directly in the root counts as the root), or else the path's first two directories (`probeMount`). A media path that is a symlink (production library files in `/media/tv` link into `/mnt/altmount`) is grouped by its link target instead (`mediaMount`), so every link into one mount shares one limit (`/mnt/altmount` when no media root holds the target) rather than one per show folder. It is computed from the path alone, apart from reading the link itself (`domain.LinkTarget`, bounded to 5 seconds, never following it): a stat to find the real device would block on the hung mount it guards against. A probe ended by the job's cancellation does not count as stuck; any other inventory refresh failure is marked only when a fresh stat of the media file also fails that way, so a missing ffprobe or LAPSE binary, pack-cache or scratch file never counts. The errno is kept, never the path. Such a failure still takes the technical-failure backoff (1 minute first) but completes with `PreserveQueueOrder`, so a storage blip does not send searches to the back of the queue. The worker counts consecutive such failures; any other completion resets the count and the pause length. Only a failure of the not-found class (`MediaUnavailableError.Missing`, `workflow.MediaMissing`: the file or its directory does not exist) can be one dead file. Before counting one, the finished job probes the storage behind it (`Worker.MediaRoots`, the configured media roots): the media file's directory, or, when that directory no longer exists, the nearest existing directory above it up to the longest media root holding it. When the media path is a symlink, its own directory is local and always lists, so the probe examines the link target instead (read with `domain.LinkTarget`, never followed, relative links resolved against the link's directory): the target's directory, or the nearest existing directory above it up to the target's root, the deeper of the media root holding the target and its first two directories (`/mnt/altmount`). An empty `/mnt/altmount` therefore counts as an outage. A directory that lists at least one entry within 10 seconds means the mount is up and only this file is missing (one Arr removed); that failure is logged as `queue.media_file_unavailable` (info) and neither counts nor resets the breaker. An empty mount point, a failed listing (`ENOTCONN`, `EIO`, …) other than a missing directory, or a probe that times out counts. Timeouts (`ErrProbeTimedOut`, a media read past its limit), read errors and mount errnos always count, whatever the listing says: altmount serves directory listings from its metadata while reads hang or fail, so a listing proves nothing about reads. Without media roots every failure counts. At three it holds all leasing, daemon dispatch and `RunOnce` alike, and logs `queue.media_paused`. The pause starts at one minute and doubles, up to 30 minutes, each time the breaker trips again before any search has read its media, so a long outage advances the backoff of a few searches rather than three every minute. The probe runs in the finished job's goroutine with its own timeout, never in the dispatcher, so a hung mount cannot block dispatch.

Before a LAPSE `nothing` or `unsure` verdict becomes a rejection, the workflow re-checks the media (`checkMediaReadable`: stat, then a 64 KiB read at the start and the middle). LAPSE hears no speech in a file it cannot read, so when the media is unavailable now the search ends with `MediaUnavailableError` (and keeps its queue position) instead of rejecting the candidate. The check is bounded by one minute (`mediaReadTimeout`); a check still blocked then (a hung mount) counts as unavailable media in the same way, and its goroutine is left blocked in the system call.

Each search job also has an overall time limit (`Worker.JobTimeout`): twice the longest one LAPSE run may take, `2 × max(sync.max_timeout, sync.timeout)`, so 8 hours by default. Later LAPSE runs on the same media reuse the speech cache, so a legitimate job stays well inside it. Past the limit the workflow's context is canceled. The worker runs the workflow in its own goroutine and waits for it at most 2 minutes more (`defaultJobGrace`); lease renewal continues until it returns or that wait ends, so the job still owns its search. A workflow that returned an error by then, or that is abandoned because it is blocked in a call that ignores cancellation (a read on a hung mount), is recorded as a timeout: `job.timed_out` is logged as a warning, the search completes as a technical failure on the failure schedule, and the worker slot is released. A workflow that returned a result in time keeps it. An abandoned workflow keeps running with its canceled context; `Installer.Install` checks the context immediately before publishing into the library, so it cannot install after its search was completed. Renewal runs on the worker's context, not the job's, so the job deadline never cuts it short. If renewal fails during the grace period (`job.lease_lost`), a job that failed or was abandoned is still recorded as the timeout: `CompleteSearch` is owner-checked, so the completion only lands while the lease is still ours, and otherwise the search would be leased again at once beside the stuck workflow.


### Site watermark cues

When `install.strip_watermarks` is true (`Installer.StripWatermarks`; default false), `Installer.Install` passes the SRT payload through `watermark.Strip` after reading it and before it is validated, compared or written (so an advert cue placed past the end of the media does not fail the five-minute overrun check, and the validated text is the installed text): whole cues (separated by any whitespace-only line) whose text, without `<...>`/`{...}` markup, is only a subtitle-site address (`titlovi.com`, `divx-titlovi.com`, `addic7ed.com` or a bare `.addic7ed.`, `podnapisi.net`, hyphens accepted for dots, `subscene`, `prijevodi-online.org`, optionally with `www.`, a scheme, `@`, spaced dots or a `Preuzeto sa`/`s` prefix), or that names `opensubtitles.org`/`.com` anywhere (its inserted adverts, in any language), or whose every line is a site address or a signature credit (`Synced and corrected by …`, `Subtitles by …`, `provided by …`, optionally after a release tag such as `WEB-DL`, or the Croatian `Transkript …` / `Hvala na transkriptu …`) with at least one address, dashes allowed (Addic7ed's signature), are dropped. In any other cue, lines that are only a site address, and a `Preuzeto sa` line directly above one, are dropped and the cue's other lines kept, unless that would empty the cue. The remaining cues are renumbered, keeping the file's line endings and a leading byte order mark. Other formats, payloads with nothing to remove, and a subtitle that would be left empty are untouched. The recorded checksum is of the stripped bytes, so ownership checks still see the file as managed and unedited. LAPSE input, candidate artifacts and rejection identities are unchanged, so no candidate is reconsidered.

## Temporary processing files

Downloads, extracted subtitles, and LAPSE synchronization output use a private `.subsyncd-work-*` directory in the system temporary directory (`TMPDIR` when set, otherwise `/tmp` in the Linux container). Standalone diagnostic LAPSE analysis uses its own private temporary copy there too. Normal workflow completion, rejection, errors, and cancellation remove the workflow directory. Rejected-candidate artifacts are released as processing advances so an uncapped exact search does not retain every attempted download.

The final `.subsyncd-stage-*` file and managed-replacement `.subsyncd-rollback-*` copy stay beside the media for atomic publication and recovery; the rollback copy is deleted once the installation is recorded. Pack-cache publication stages within the persistent pack-cache root; LAPSE speech profiles also remain in the persistent data directory. Moving scratch to a separate filesystem does not change either atomic publication path.

Application errors redact the effective temporary root. LAPSE failures expose bounded verdict, exit-code, and protocol/operation categories; raw stderr, JSON diagnostic values, and command errors are not included. No-speech detection still classifies the failure internally without logging the diagnostic output.

The Compose example supplies a 512 MiB `/tmp` tmpfs shared by active workflows. Increasing workflow concurrency may require increasing that temporary-storage allowance. Do not point `TMPDIR` at a media-library directory if temporary subtitles must remain invisible to library scans. Abrupt process/container termination can bypass deferred cleanup; container tmpfs is discarded when its mount is recreated. This change does not scan or remove legacy `.subsyncd-work-*` directories from media roots.

## Startup and health

Startup is deliberately offline with respect to Arr, subtitle providers, and Silo. It fails only for invalid configuration, unsafe/missing local roots, SQLite migration/open errors, missing `ffprobe`, or an incompatible LAPSE executable. Configuration must contain exactly one non-empty YAML document: cardinality is checked on the original bytes before environment expansion, so a trailing document is rejected without expanding or exposing its values. Empty trailing separators are harmless. Run diagnostics after every configuration/image change:

```bash
subsyncd doctor --config /config/config.yaml
```

`GET /healthz` means the HTTP process is alive. `GET /readyz` rechecks SQLite and media-root availability. Temporary provider or Arr failures do not make readiness fail; they are scheduled and logged instead.

Provider network errors and HTTP 5xx responses are circuit-broken per provider instance and operation with persisted 1, 5, 15, and 60 minute retries. A provider-supplied `Retry-After` overrides that delay. Interrupted response bodies also participate in provider failure backoff; caller cancellation and local output failures do not. Definitive login HTTP 401 from OpenSubtitles/Titlovi and a SubDL HTTP 401 from its own API or download host, or HTTP 403 whose message says the API key or (non-download) token is invalid, banned, revoked, expired or unauthorized, disable the affected instance (any other SubDL 403 opens the transient circuit) until its credentials are corrected and the operator clears provider state (substitute that instance name below):

```bash
subsyncd retry --config /config/config.yaml --provider subdl-main
```

The retry command clears all cooldown, quota, transient-failure, and disabled-authentication scopes for that one configured provider; it does not alter candidate rejections or search schedules.

## Sonarr and Radarr setup

Each instance needs a unique `name`, API key, and one or more remote-to-local path mappings. Longest boundary-aware mapping wins. Mapping destinations must sit inside a configured media root, and existing parent symlinks are resolved before acceptance.

With `server.webhook_base_url` set, the daemon manages the Arr connection itself (below). Otherwise create an Arr webhook/connection pointing to the URL printed by `subsyncd webhook-url --instance INSTANCE_NAME --base URL` (without a base, from `--base` or `server.webhook_base_url`, only the path and query are printed):

```text
http://subsyncd:8097/webhooks/INSTANCE_NAME?token=STORED_WEBHOOK_TOKEN
```

Enable download/import (including upgrades), rename, file-delete, and whole-movie/series-delete events. Any other event type (grab, health, series or movie added, application update, and the other app's whole-delete events) is answered HTTP 204 as ignored, so a connection with extra events enabled is not reported as failing; a payload that is malformed or lacks the identity its event needs is HTTP 400.

A valid webhook is answered as soon as it is durably stored: HTTP 202, `webhook.queued`. The body is kept in `webhook_inbox` (migration 020) with its receipt time, and `catalog.WebhookInbox` applies it in the background. One processor per instance applies that instance's webhooks in arrival order, so one media item's changes keep their order and concurrency is bounded by the number of instances; Arr lookups no longer hold the HTTP request. A webhook whose processing fails (Arr unreachable, SQLite busy) is retried after 1 minute, 5 minutes, 15 minutes, 1 hour, 6 hours, then 24 hours, while later webhooks continue; after six attempts it is abandoned (`webhook.failed`, `outcome=abandoned`) and reconciliation from Arr history covers the change. When the inbox itself fails (it cannot be read, or a webhook cannot be deleted or rescheduled: a full disk, a read-only database), the processor logs `webhook.failed` with `outcome=inbox_unavailable` and waits 5 seconds, doubling up to 5 minutes, before the next pass, ignoring wakes from new webhooks meanwhile; a pass that succeeds resets the wait. Without it, a webhook that stayed due would be applied against Arr again at once, over and over. Webhooks stored for an instance that is no longer configured are not processed; startup logs `webhook.inbox_orphaned` (warn) with the count per such instance, and `forget-instance --yes` deletes them with the instance's other records. Webhooks still stored at shutdown, or left by a crash, are applied at the next start. Each change is dated by its receipt time, and a delete records its time on the media row (`deleted_at_ns`, migration 021, set only by deletes; rows already deleted take their `updated_at_ns`): an import or rename is skipped when a delete applied after the change happened removed that same file, or removed the whole movie or episode (a delete without a file id: MovieDelete, SeriesDelete, or history finding no current file, which also records `entity_deleted_at_ns`, migration 021; rows deleted before it keep 0), so a retried or late upsert cannot revive a deleted row. A delete of another file of the same movie or episode never blocks it: when an upgrade's import is retried after the old file's delete was applied, the new file still revives the row. A change that happened after the delete (a real re-import) applies as before. `updated_at_ns` is not compared, because inventory refreshes and other writes move it: a row refreshed after the change would otherwise make a later re-import look older than the delete. Keep the token out of general reverse-proxy access logs. `subsyncd` itself logs only `/webhooks/INSTANCE_NAME`, never the query string. The request body limit is 1 MiB.

An import or rename whose hydrated media is deliberately outside the configured path mappings returns HTTP 204 as ignored. It creates no audit mutation, media/search row, or worker wake. This permits a normal Arr connection to target a narrow canary without causing retries for the remainder of the library. Only the typed scope condition is ignored: traversal, unsafe filesystem resolution, Arr transport/authentication, and SQLite failures still return an error. File-delete webhooks remain file-ID addressed. Radarr `MovieDelete` resolves `movie.id` as a stable movie entity inside the deletion transaction. Sonarr `SeriesDelete` resolves `series.id` against persisted `media.series_id`; all matching episodes, searches, and per-episode audit records commit atomically. Neither event hydrates deleted Arr objects, accesses media files, or uses the `deletedFiles` flag to decide whether to retire catalog work. Unknown identities are audited idempotently without changing unrelated media. Migration `004_sonarr_series.sql` adds series identity to media and audit rows; legacy media defaults to zero and acquires its series ID through ordinary hydration, never a startup backfill. Whole-series deletes deliberately do not match those unknown legacy rows by title, path, or external ID.

Startup assembly remains offline: it creates no Arr client traffic and performs no full-library scan or identity backfill. Each instance reconciles every six hours using an independent persisted cursor; the first check after the daemon starts runs only the instances that are due by their saved timing. A failed attempt retains that cursor and retries after 5 minutes, 15 minutes, 1 hour, then every 6 hours until success. The attempt time, failure count and deferral flag are saved on the instance row (`instances.reconcile_attempted_at_ns`, `reconcile_failures`, `reconcile_deferred`, migration 020), so a restart keeps the schedule: it neither repeats a reconciliation that just ran nor forgets a failure backoff. An instance never reconciled is due at once, and so is one whose last reconciliation succeeded but whose library discovery is pending again at startup (its discovery scope changed: type, URL, mappings, roots or the scope version); a failure backoff or a deferral keeps its saved timing, and the check runs once per start. One failed instance neither advances nor delays another.

A page that commits but defers entities whose current media cannot be read (`ErrHistoryDeferred`, typically a broken symlink into a FUSE mount) is not a failure. Catalogs return a typed `DeferredHistoryError` listing each entity with a log-safe title from `observability.MediaTitle`; Sonarr fetches series titles best effort, once per series, only for the ten entities that are logged, and stops after the first failed lookup. The nondeferred mutations commit through the replay table and the cursor is retained as before. Library enumeration (`ListLibrary`) defers the same way: unreadable files are skipped and reported (a Sonarr file before its episodes are read is labelled by file ID, series title and season), the readable media commit through `CommitPartialLibraryDiscovery`, and the discovery scope stays incomplete so the next reconciliation enumerates again; a mount outage therefore cannot mark skipped files as discovered. A deferred discovery no longer stops `Run`: history still reconciles, and both deferrals are merged into one `DeferredHistoryError`. The worker and `scan` decide on the `ErrHistoryDeferred` sentinel and use the typed error only for labels. The worker logs `reconcile.deferred` and retries after one hour (or the normal interval, if shorter) without escalating the failure backoff; a later real failure starts that backoff at 5 minutes. There is no time limit: the cursor stays until every deferred entity's media is readable or Arr no longer reports it. `scan` reports deferred entities in its summary instead of failing.

Reconciliation uses `github.com/cplieger/arrapi/v2` v2.0.5 for bounded, retried history and current movie/episode requests. History is fetched in descending 100-record pages, with strict page-count, ordering, and progress checks; malformed or inconsistent pagination does not advance the cursor. Mapping a path whose lookup fails with a mount error (`domain.MountUnavailable`: `ENOTCONN`, `EIO`, `ESTALE`, `EHOSTDOWN`, …), on the path itself, a parent or the media root, is `errMappedPathUnavailable`, like a dropped mount: the entity is deferred rather than failing the page or being treated as removed. Other errors (permissions, traversal) still fail the page. History is grouped by stable Arr entity (`movieId` or `episodeId`), not replaceable physical file ID, and current state decides whether that entity is present, absent, or outside the configured scope. The detail client rejects redirects even within the same origin and exposes only bounded error categories, preserving cancellation and timeout identity. It is retained only to enrich live files with release, quality, edition, runtime, and provenance fields not exposed by arrapi v2.0.5. Each run also compares a complete top-level identity snapshot (Sonarr series or Radarr movies) with active identities and retires absent ones. When at least two identities are active and the snapshot would retire all of them, or more than half and at least `massDeletionMinimum` (10), the snapshot deletions are withheld for that run while history mutations and the cursor still commit; `reconcile.snapshot_deletions_withheld` is logged. Zero overlap alone is not the test: a rebuilt or different Arr instance numbers from 1 and shares low IDs by coincidence. Rediscovery never revives deleted rows, so an empty or foreign Arr database must not be able to delete the catalog.

Imports, renames, upgrades, deletion tombstones, audit rows, media/search changes, and the new cursor commit in one SQLite transaction. Arr history requests have second resolution, so subsyncd rounds the durable cursor down and intentionally overlaps its fractional second; stable history event IDs make the replay transactionally idempotent. History also contains every change a webhook already delivered, under a different event ID, so reconciliation marks its import and rename mutations `Replay`: one whose file (same instance, kind, file ID and entity) is already active with the same path, size and unsupported reason, and whose media row was last updated at or after the history record's time (as a webhook's apply time always is), is recorded and linked but does not reopen its searches. The check reads only the media row, so audit-log pruning cannot defeat it. Any difference, a deleted row or a history record newer than the row reopens them as before; webhook, library-discovery and multi-episode re-check events are never treated as replays. A malformed or otherwise failed page advances nothing. When a media path changes, managed installation paths (and rollback copies in the same directory) are rebased to the new media stem in the same transaction, including for upgrades that replace the content; an upgrade then also clears the installation's media provenance, so a sidecar carried over to the new name stays managed and is reassessed instead of being treated as user-owned. Root remote mappings (`/`) remain valid. Webhook batches skip outside-scope items individually and continue later relevant items; retained committed event IDs are checked before hydration so exact redeliveries do not depend on the old file remaining available. Deliberately unmapped or safely out-of-root media is consumed as an outside-scope delete/audit, which keeps a narrow canary from reading or indexing the rest of the library; unsafe mappings and filesystem errors fail the page closed.

subsyncd supports only the current lineage beginning with `001_baseline.sql`, followed by its ordered embedded migrations. A database containing any migration name from the pre-release `001_initial.sql`–`010_media_entity_ids.sql` lineage fails startup with an explicit unsupported-lineage error. Stop the service, preserve or move the complete old data directory for rollback, create an empty data directory with the configured container ownership, and let a mutating command initialize the current schema. `serve` performs that initialization locally before starting runtime work; after initialization, `doctor` can inspect the database while the daemon runs. Do not copy rows between lineages.

Migration `002_scrub_provider_credentials.sql` removes provider-derived cache, candidate, pack, installation-provenance, and rejection rows whose persisted fields contain a legacy `api_key=` query. It preserves media inventory, search schedules and active leases, reconciliation cursors, and unrelated clean provider rows; deleting a contaminated pack cascades only its cached members. Subtitle files already installed on disk remain in place when contaminated installation provenance is removed, but they become protected untracked sidecars and cannot be upgraded as service-owned files. Rotate any SubDL key used by an affected build before starting the corrected image.

Migration `003_inventory_probes.sql` adds completed-probe fingerprints and retained media deletion state. Existing track rows do not become completed probes automatically: their next normal refresh probes the file once, then caches the result. The migration preserves a historical deletion only when at least one retained search exists, every search is terminal with outcome `deleted`, the latest linked applied import/rename/delete event by insertion order is a delete, and that delete timestamp is at least the media update timestamp. This positive local evidence blocks claims, inventory, and installation commits until reimport. A stale removed-language outcome alone is insufficient; later imports/renames and newer direct media updates prevent inference. Missing/pruned audit evidence, absent searches, or mixed search outcomes remain ambiguous and retain the active default. There is no startup scan, probe, identity backfill, or network request.

Ordinary and forced scans enumerate only active media, so retained tombstones do not inflate counts or abort probing of later active files. A deletion after enumeration still fails the inventory compare-and-swap guard technically. Configured-language backfill creates no work for known tombstones; retained media, searches, provenance, and audit rows remain available.

Every persisted media row has a positive stable Arr entity ID. Physical file ID remains separate and replaceable for hashes, inventory, installations, and webhook processing. Startup remains offline and performs no Arr request, identity backfill, or full-library scan. The migration runner remains active for schema changes added after `001_baseline.sql`.

The daemon starts with one media workflow at a time. Increase this only when the host and media storage can sustain concurrent provider preparation and LAPSE reads:

```yaml
worker:
  max_concurrent: 1 # valid range: 1..8
```

Search work is durable and strictly ordered by class: a newly imported or renamed file runs before an ordinary missing-subtitle retry, which runs before a scheduled upgrade check. Reconciliation, including first-run library discovery, also runs instances in `queue_priority` order (highest first, ties by name), so on a fresh database the highest-ranked library is queued first. Within one class, instances with a higher `queue_priority` (0–1000, default 0) win, then the oldest queue position, then the oldest due time, then media order, then media ID and language. Media order is title (lowercased with SQLite's `lower()`, which folds ASCII letters only, so accented capitals keep their case and accented initials sort after `z`), then Sonarr series ID (so two shows with the same title stay apart), then season (movies use their release year instead; specials, season 0, follow every regular season), then episode. It matters because a library discovery, scan or newly configured language queues its whole batch at one queue position; it makes that batch run show by show from S01E01, specials last, and movies alphabetically with remakes oldest first, instead of in the order the Arr listed the files. Migration `017_search_media_order.sql` copies those values onto each search as `sort_title`, `sort_series`, `sort_season` and `sort_episode` (backfilled once with a join on `media`), replaces 014's insert trigger with one trigger, `search_states_queue_order`, that fills `instance_rank` and the media order in a single update, adds `media_search_order` to keep the copies in step when a media row's title, series ID, year, season or episode changes, and rebuilds `search_due_idx` as `(state, priority DESC, instance_rank DESC, queue_order_ns, next_attempt_at_ns, sort_title, sort_series, sort_season, sort_episode, lease_until_ns)`, so the order still comes from the index. Like every migration, 017 can't be rolled back: an older image refuses a database that has it applied, so back up `subsyncd.db` before deploying it. Queue position (`queue_order_ns`) equals the due time on every write except a throttled completion, which keeps it, so a provider reset with jitter changes when a search is eligible but not where it sits in the queue. Migration `014_search_queue_order.sql` adds the column, copies every existing due time into it so current order is preserved, adds `instances.queue_priority` and `search_states.instance_rank`, and rebuilds `search_due_idx` as `(state, priority DESC, instance_rank DESC, queue_order_ns, next_attempt_at_ns, lease_until_ns)`, so the lease order comes from the index. Startup stores each configured instance's `queue_priority` and re-ranks existing searches in one transaction (unlisted instances rank 0); an insert trigger copies the rank onto new searches. A manual-search upgrade schedule keeps an earlier queue position rather than moving a pending search back. While every provider on a language route is unable to download, the daemon leases nothing for that language and media kind (see the provider reference). A webhook sends a nonblocking advisory wake after its database commit, so a free slot is filled without waiting for the next poll. Wakes may coalesce during bursts; startup and the jittered recovery poll read SQLite again, so correctness never depends on receiving every signal. A new event for a media/language already being processed requests exactly one immediate rerun without starting a concurrent duplicate. Priority changes dispatch order only and never bypass provider rate limits or persisted cooldowns.

To add an Arr instance or language, edit the configuration and restart subsyncd. A new instance receives an empty reconciliation cursor and an incomplete full-library discovery marker. Background maintenance enumerates all current in-scope files once before history reconciliation, including files absent from history; configure its webhook as well for immediate future changes. Migration 005 also makes existing instances eligible for this one-time pass. Explicit scan repeats additive discovery. Completion is keyed by instance type/URL/mappings/roots; changing scope permits another pass. Discovery commits only missing entity/file identities, preserves existing rows and schedules, and never infers deletions from snapshot absence. An event revision captured before enumeration is compared transactionally before imports and completion; a concurrent webhook makes the snapshot retry without publication. Empty successful snapshots count as completed. A newly added language is backfilled locally for active media subsyncd already indexes under currently configured instances. Those checks are immediately due at missing priority, but embedded or protected subtitles can satisfy them without a provider request. Existing search schedules, leases, attempts, installations, and other-language state are preserved.

The same lease rule applies to reconciliation. If history reports a change for media already being processed, the current owner and expiry remain intact and one immediate rerun is coalesced. An old completion cannot erase that rerun.

For a missing language, search workflows run at absolute milestones from import or reset: immediately, about 30 minutes, 2 hours, 8 hours, 24 hours, 3 days, 7 days, 14 days, and every 14 days thereafter, with interval jitter. Sidecars are refreshed on every run. Provider search results are cached for six hours, so the 30-minute and 2-hour workflows normally perform local checks without another provider request; under an unchanged empty result, external searches normally occur around import, 8 hours, 24 hours, 3 days, 7 days, and 14 days. Provider cooldowns and technical-failure retries remain independent of this sequence.

### Webhook tokens

Webhook authentication tokens are generated by subsyncd, never configured: `webhook_token` in the configuration is refused at load with an error naming the instance and never the value. Migration 022 adds four columns to `instances`: `webhook_token` (empty until generated), `webhook_connection_id`, `webhook_connection_arr_url` (the Arr base URL the ID was recorded against) and `webhook_checked_at_ns`. The mutable assembly (`serve` and the mutating commands) calls `EnsureWebhookTokens` after migrations and the instance rows exist: 32 bytes from `crypto/rand` as 64 lowercase hex characters, stored once and added to the redaction set. Read-only assemblies never generate, migrate or write; `webhook-url` on a database with no token yet fails and asks for one start. `rotate-webhook-token` takes the mutation lock, so the daemon cannot be running, and replaces the token in one statement. Its output tells the operator to start subsyncd: with `server.webhook_base_url` set, the sync at that start rewrites the managed connection; otherwise the operator runs `webhook-url --base` and updates Arr by hand. `doctor` reports `webhooks: manual` or `webhooks: managed (<base url>)`.
Migration `023_live_control.sql` adds the search history and the columns the live control commands read. `search_history` keeps one row per finished search: the media reference (`instance`, `kind`, `file_id`) and `media_title` copied at the time, `language`, `outcome`, the winning or last candidate's `provider_id` and first `release_name`, a `reason` (empty unless the code has a natural one, such as the manual-timeout marker), `manual` and `finished_at_ns`, indexed on `finished_at_ns`. `media_id` is `ON DELETE SET NULL`, so a row outlives its media row with its title and reference intact. A worker completion writes its row inside the `CompleteSearch` transaction, after the owner guard succeeds, so a lost lease writes nothing; a completion with outcome `deleted` writes none. A manual search writes its row with `manual=1` right after the run (and the timeout path through `CompleteSearch`), outside the installer's transaction: a crash between installing and that write loses one history row and nothing else. Titles come from the same helper as the `media_title` log field, and rows hold no paths, provider text or credentials. The daemon's hourly maintenance (the ticker that also prunes the LAPSE cache) deletes rows older than 30 days (`store.HistoryRetention`); a failure logs `history.prune_failed` (warn) and is retried the next hour. A manual search records its row last, after the lease release and upgrade scheduling, and a failed write logs `history.record_failed` (warn) instead of failing the search. The migration also adds `installations.candidate_signature` and `installations.artifact_checksum` (the values `candidate_rejections` uses for the same candidate, recorded when the subtitle is installed) and `search_states.replace_installed` (0 or 1: a reject's replacement is queued; see [Reject, replacement and removal](#reject-replacement-and-removal)). Installations that predate the migration keep empty signature and checksum: there is no startup scan and no network request, and nothing is backfilled. Like every migration, 023 can't be rolled back: an older image refuses a database that has it applied, so back up `subsyncd.db` before deploying it.

### Managed Arr connection

When `server.webhook_base_url` is set (one setting for every instance), `WebhookConnectionMaintainer` runs beside the inbox processor and the worker. Startup and readiness make no Arr request. It never takes `reconcileMu` or touches reconciliation state.

`WebhookConnectionSync` finds the one connection subsyncd owns for an instance, in this order:

1. Ownership by remembered ID: the stored connection ID, recorded against the same Arr URL, that still exists as a `Webhook` implementation whose unescaped URL path ends in `/webhooks/<instance>`. Host and token may differ and are repaired. When the path does not match (an ID reused after Arr's database was reset or reinstalled can name another webhook), the remembered ID is ignored and adoption or creation follows as if nothing were remembered.
2. Adoption: a `Webhook` connection whose URL path ends in `/webhooks/<instance>` and that is positively ours, meaning it carries the stored token, or it has the same origin as the base URL (scheme, host name, effective port, so `:80` and `:443` equal the default) at exactly `<base path>/webhooks/<instance>`. A second deployment behind the same proxy differs only by path prefix and is therefore never adopted or rewritten. More than one match logs `webhook.connection_ambiguous` and changes nothing; matches of the path that are not ours are counted as `webhook.connection_foreign`.
3. Create: a copy of Arr's `Webhook` schema template named `subsyncd (<host:port of the base URL>)`, every event flag off except the required ones for which the template's matching `supportsOn...` is true.

The desired URL is `<base without trailing slashes>/webhooks/<PathEscape(instance)>?token=<token>`. Repair sets only the managed keys: the `url` field, the `method` field (POST) and the required event flags. Resources are handled as raw JSON, so every other key (name, tags, other events, headers, unknown future keys) round-trips unchanged; `changed` names only the groups it set. Required flags: Sonarr `onDownload`, `onUpgrade`, `onRename`, `onSeriesDelete`, `onEpisodeFileDelete`, `onEpisodeFileDeleteForUpgrade`; Radarr `onDownload`, `onUpgrade`, `onRename`, `onMovieDelete`, `onMovieFileDelete`, `onMovieFileDeleteForUpgrade`. Notification resources have no `enable` key: a connection is enabled when any event flag is on. `forceSave` is never sent.

Arr tests the webhook URL on every save with any event flag on, and `forceSave` does not skip it. A failed test answers 400 (typically a `Url` property error: subsyncd answered the test call with an error) or 500 (Arr could not reach subsyncd), mapped to `arr_test_unreachable` for 500 and `arr_test_rejected` for any 400 validation error other than the Name collision below (other statuses are `arr_status`). Arr's own HTTP proxy settings apply to that call, so a proxy must let subsyncd's address through. Both bodies echo the URL with the token, so the client reads a 400 body only for `propertyName` values and drains and discards every other non-2xx body unread. Connection names are unique in Arr: a 400 whose only property is `Name` retries with ` 2` through ` 9` appended, then fails with `name_unavailable`.

The schedule: all instances are due at start; each sync is bounded at 60 seconds and instances sync sequentially, so one slow Arr delays the others by at most its own bound. After success the next check is 6 hours away. After consecutive failures of one instance the retry delays are 15 minutes, 1 hour, then 6 hours until a success resets the count. Each failure logs `webhook.connection_sync_failed` once with `reason` and `status`; a failure that is not a `WebhookSyncError` logs `reason=internal` plus `ErrorAttrs("webhook_connection_sync", err)`, cleaned by the emitter's redactor. Arr runs its save-time test inside the POST or PUT, so a test call to `server.webhook_base_url` that hangs exhausts the client's 15-second request timeout and is reported as `arr_unreachable`. After each successful create, adopt, repair or no-op check, the connection ID, Arr URL and check time are recorded; an ambiguous match records nothing, counts as success for the schedule, and warns again at the next check.

## Embedded and external subtitle behavior

FFprobe indexes all embedded subtitle streams, including text and image codecs. A separate completed-probe fingerprint records successful probes, including empty results; catalog metadata alone never establishes cache validity. The result is reused until path, Arr file ID, size, or nanosecond mtime changes. Inventory commits compare the original catalog snapshot transactionally and recheck live media after probing, so stale work cannot restore a replaced or renamed file identity. Sidecars are never trusted from that cache: `.srt`, `.ass`, `.ssa`, and `.vtt` files for the exact media stem are scanned and checksummed before every search.

An embedded track also counts as forced when its title carries an explicit label such as `English [Forced]`, even without the container's forced disposition. Negated labels such as `not forced` and `forced subtitles removed` do not add forced status, and an explicit container disposition always takes precedence. Stored tracks do not retain their original titles, so changing this classification requires invalidating completed-probe markers; files are then probed again on their next scheduled or manual search.

A matching full embedded track prevents downloading. Forced-only or unknown-language (`und`) tracks do not. SDH/HI tracks are rejected by default and satisfy only when `allow_hearing_impaired: true` is explicitly configured. Existing sidecars are protected unless their path and checksum match `subsyncd` installation provenance, so user edits are never overwritten automatically. A sidecar that is a symbolic link to a regular file is always a protected track (`inventory.Track.Symlink`), even when its path and checksum match provenance: it satisfies its language before any provider is asked, and nothing is ever written or removed through it. A dangling link is not a subtitle and is ignored; the installer still refuses to publish over it.

Stored provenance is historical evidence, not proof that a sidecar still exists. Each workflow refreshes live sidecars and treats a managed installation as active only when its recorded path and checksum are present. If that managed file was deleted, the record is dropped (`install.record_dropped`) and normal acquisition runs with first-install semantics and can reacquire the same exact candidate. If a sidecar named after the media file is present but its checksum differs, it remains protected as user-owned content and is not replaced; a record whose checksum no longer matches a sidecar of another name, or one recorded for a replaced media file, is dropped instead (see [Replaced and renamed media files](#replaced-and-renamed-media-files)).

When the live inventory finds the media file changed in place (same path and Arr file ID, different size or mtime, without an Arr event), `ReplaceTrackInventory` clears installation provenance as before. Only a different size counts as a replacement: then every other language with an installation is made due at once at import priority, unless that search is leased (the running search handles its own language). Its attempt counters and last outcome are kept; the search that runs replaces the outcome. An mtime-only change re-queues nothing, since a remount, metadata repair or mount upgrade can touch the whole library without changing any bytes, and re-searching would stream every file through LAPSE. A subtitle timed for the old file is therefore re-checked promptly: without provenance for the current bytes, any eligible candidate may replace it. Replacements that Arr reports already reschedule every language through the import event.

Sonarr can associate more than one episode with a single media file. `subsyncd` records such a file using the earliest episode as its canonical stable entity. When the episodes are consecutive within one season, the file is a range: migration `015_multi_episode_range.sql` adds `media.episode_end` and `media.absolute_episode_end` (absolute numbers are kept only when every episode has a consecutive one), searches run normally, and `subsyncd explain` shows `episodes=S06E01-E02`. Otherwise the file persists `unsupported_multi_episode` with `episode_end = -1` (checked), every configured language is terminally marked, and provider, LAPSE, installation and upgrade work are skipped. Rows marked unsupported before ranges existed (`episode_end = 0`) are re-hydrated once by the next Sonarr reconciliation and committed as an import, which stores the range and schedules searches or records the checked marker; a failed hydration logs `reconcile.multi_episode_recheck_failed` (warn) and is retried on the next reconciliation. The re-check's event ID is stable per file, so a retried commit applies it once. A later import or rename re-evaluates the file.

## LAPSE policy

LAPSE v2.2.4 is the compatibility baseline. Exact OpenSubtitles hash matches always bypass it. With the default `sync.policy: confidence`, a non-pack first install also bypasses LAPSE when its release score is at least 75 and the score contains an identity anchor (external ID or normalized title/year), a release-group match, and explicit episode evidence for TV. Provider rating and popularity can add points but cannot replace those required anchors. The stored sync verdict is `score_bypass`, so `explain` distinguishes this decision from an exact hash and a LAPSE result.

Packs and managed-subtitle upgrades still require LAPSE by default, even if their score is high. Candidates below the bypass score or missing any required anchor also require it. If Radarr identifies a movie edition, a non-hash candidate must explicitly match its cut or, for an edition with no cut such as IMAX, all of its picture variant labels to bypass LAPSE; an edition with neither (e.g. Criterion) does not restrict the bypass; an unknown edition remains eligible but requires LAPSE, while a known mismatch is rejected. Set `sync.policy: always` to restore LAPSE for every non-exact candidate. The individual `require_*` and `lapse_for_*` switches are configurable for unusual libraries, but relaxing them increases the chance of installing a wrong or unsynchronized subtitle.

`sync.policy: never` disables LAPSE for every non-exact candidate, including provider packs, runtime packs, upgrades, and edition-unknown candidates; the bypass score and every `require_*`/`lapse_for_*` switch are ignored. Eligibility, identity rejection, the minimum score, upgrade deltas, archive selection, and subtitle validation are unchanged. The stored verdict is `sync_disabled` (mode `bypass`, reference `policy`) and `candidate.selected` logs `selection_mode=sync_disabled`. Because versions are ranked by LAPSE confidence, a pack supplying more than one version of the requested episode is recorded as a `pack_selection` rejection (rule `versions_ambiguous_without_sync`) instead of installing an arbitrary member. The policy is part of the rejection tool signature, so changing it lets earlier timing and version-ambiguity rejections be reconsidered. LAPSE remains a startup and `doctor` requirement.

When LAPSE is required, each candidate is prepared once with a new explicit output using `--output`, `--no-backup`, `--json`, `--strict`, and `--no-sidecar`. The same invocation supplies both the decision metrics and synchronized artifact. Only a `solid` result with a valid written output can install; malformed protocol output is a technical failure.

The best three eligible non-hash candidates are a cap, not an eager batch. They are partitioned by release score and processed from highest score downward. A unique top scorer is prepared alone; if it installs, lower tiers are never downloaded. Candidates tied at the same score are all prepared so LAPSE confidence can choose the best. The winner's retained output installs directly without another LAPSE call. Other viable outputs remain available for candidate-local installation fallback; only an exhausted tier opens the next lower score. Original source checksums identify rejections, and cached pack sources remain immutable. Deterministic verdict/content failures retain their scoped quarantine behavior, while process, filesystem, provider, network, and cancellation errors remain retryable and never blacklist a candidate except for the narrow repeated silent exit described below.

An `unsure` or `nothing` verdict retains a rejection for that provider result without time expiry, scoped to the language, exact media fingerprint, stable candidate/release metadata, selected artifact checksum when known, LAPSE compatibility version, and synchronization policy. Invalid or oversized subtitle payloads and ambiguous, missing, or explicitly conflicting episode-member selection are quarantined too. Invalid generated LAPSE subtitle content is retained as `lapse_invalid_output`; this includes invalid timestamps even when LAPSE reports solid. Process, protocol and filesystem failures remain retryable. This is candidate-local and does not throttle the provider. Rejected candidates are removed before the three-candidate shortlist, so later-ranked results advance on the next job. A rejected cached pack member is skipped by checksum; the pack remains available to other episodes.

LAPSE-generated cues with valid intervals but decreasing start times are stably reordered before final validation. Complete cue records retain their timestamps, text, styling and identifiers; equal-start cues retain their order. Negative or reversed intervals still reject as `lapse_invalid_output`.

A candidate-local subtitle validation rejection during installation advances to the next prepared tie or score tier, with rejection evidence based on the original selected subtitle. A format-changing upgrade also advances without replacing the managed sidecar. Filesystem, stale-media, database, and rollback failures stop installation. The installer checks the media file immediately before publication, and the installation/outbox transaction checks the stored path, Arr file ID, size, and modification time; a media replacement during LAPSE cannot commit obsolete provenance or notification intents.

At debug level, `candidate.rejected` reports bounded archive-selection fields: `reason_code`, `selection_rule`, `archive_type`, `subtitle_member_count`, and `matching_member_count`, together with provider and candidate ID. Archive filenames and absolute paths are deliberately omitted.

Migration `013_repeated_lapse_failures.sql` persists a bounded strike only when a selected artifact with a checksum returns a direct or unary `%w`-wrapped LAPSE `ProcessExitError` with exit code 2 and completely empty stdout and stderr. The first matching observation is still a technical failure and uses the ordinary failure backoff. A second observation in a separate workflow attempt with the identical media fingerprint, candidate/member identity, artifact checksum, LAPSE compatibility/policy signature, and `exit_2_empty_output` failure signature atomically writes the ordinary permanent rejection `lapse_repeated_empty_exit` and deletes the strike. One immutable rejection/artifact identity is prepared and counted at most once per workflow attempt across pack cache, exact, broad, preferred, and fallback acquisition, so a cache/provider duplicate cannot confirm its own first strike. After confirmation the workflow advances through its normal candidate/version/provider progression without another invocation. Changed media, candidate, member scope, artifact, LAPSE version, or policy cannot inherit a strike. `search --retry-rejected` and any path that clears candidate rejections clear both durable states for its selected media/language; routine searches leave strikes alone, and `explain` reports only confirmed rejections.

Composite or multi-cause failures containing a process exit remain technical as a whole, even when another cause is a deterministic verdict, archive selection, subtitle content, no-speech result, cancellation, filesystem, or protocol error. They create neither a strike nor an immediate candidate rejection. The first `syncer.TimeoutError` in a workflow attempt is latched on the request (`lapseTimeout`, shared by member, pack-cache and fallback-tier requests of that attempt). The time goes to decoding the media, and LAPSE writes no speech profile for an unfinished run, so every later LAPSE run for that file would hit the same limit: later non-exact candidates reaching `SynchronizeCandidate` get the latched error without a run. Exact-hash candidates and policy bypasses never read the media and proceed normally, including in the fallback tier. The latched errors are ordinary technical candidate failures, so an attempt that installs nothing ends as exhausted acquisition with failure backoff, reported as `lapse_timeout`. `TimeoutError` is returned only when the run's own limit expired, never when the caller's context ended first. Timeouts, crashes, diagnostic-bearing or malformed LAPSE output, cancellation, runner/protocol/filesystem failures, missing checksums, and provider/network failures do not quarantine the candidate. They surface as technical failures and use the separate failure backoff. Direct no-speech remains a media-validation rejection rather than evidence that one particular subtitle is bad. In every failure case, the job workspace is removed and an existing installed subtitle remains untouched.

LAPSE itself makes no internet request, but it reads the media to build a speech profile; on network storage, the first LAPSE invocation can therefore read much or nearly all of the file. The profile cache is persisted under `/data/lapse-cache`, so later candidates for the unchanged media can reuse it. The top-level `lapse_cache.ttl` defaults to `720h` and must be positive. Mutating assembly prunes expired entries once; daemon serving checks hourly. Age is measured from filesystem mtime (last profile write), with no cache-hit refresh. The shared LAPSE instance excludes cleanup with its runner lock; an active invocation skips the sweep until the next check. Cleanup uses rooted directory operations, validates root identity, rejects a symlink root, and removes only regular files named `<16 lowercase hex>.spans` or `.spans.tmp` at or beyond the cutoff. It does not traverse directories or follow entry symlinks. Cleanup is best-effort: `lapse.cache_cleanup_failed` is a bounded warning; successful removals are debug-only `lapse.cache_cleaned` with `removed_count`, without paths or filenames. Diagnostic assembly never prunes persistent profiles. The confidence gate avoids that media read for strong first-install matches. Each run is limited to `sync.timeout` (default 30 minutes) or, when larger, the media size divided by `sync.min_read_rate` (default 4 MiB/s), stat'ed when the run starts, capped at `sync.max_timeout` (default 4 hours or `sync.timeout` if longer; configuring it below `sync.timeout` is rejected). The comparison is made in seconds before conversion, so extreme sizes or rates cannot overflow. An unreadable size keeps `sync.timeout`. Cancellation kills the entire LAPSE subprocess group.

With distinct candidate scores and a successful leader, the expected path is one LAPSE invocation. Three viable tied candidates require up to three invocations: a solid result with confidence of at least 0.9 and full agreement and coverage is accepted at once, the rest of its tier is not checked (`candidate.early_accepted`, info), and sorting still installs the best prepared result. Exact-hash and policy-qualified score bypasses require none.

Diagnostic analysis remains a read-only `--dry-run` on a private copy and never installs a sidecar:

```bash
subsyncd analyze-sync --config /config/config.yaml --media /media/movies/Movie.mkv --subtitle /tmp/candidate.srt
```

## CLI reference

The default configuration path is `/config/config.yaml`; set `SUBSYNCD_CONFIG` or pass `--config` to override it.

```bash
subsyncd serve --config /config/config.yaml
subsyncd scan --config /config/config.yaml --instance sonarr-main
subsyncd scan --config /config/config.yaml --instance sonarr-main --force-probe
subsyncd search --config /config/config.yaml --instance radarr-main --kind movie --file-id 42 --language en
subsyncd search --config /config/config.yaml --instance radarr-main --kind movie --file-id 42 --language en --retry-rejected
subsyncd search --config /config/config.yaml --title "Show S01E01" --timeout 4m --json
subsyncd reject --config /config/config.yaml --title "Movie (2019)" --language en --reason out_of_sync --json
subsyncd reject --config /config/config.yaml --title "Movie (2019)" --language en --undo
subsyncd retry --config /config/config.yaml --provider titlovi-main
subsyncd explain --config /config/config.yaml --instance sonarr-main --kind episode --file-id 1001 --language hr
subsyncd explain --config /config/config.yaml --title "Show S01E01"
subsyncd find --config /config/config.yaml --path /tv/Show/S01E01.mkv
subsyncd doctor --config /config/config.yaml
subsyncd analyze-sync --config /config/config.yaml --media /media/tv/Show/S01E01.mkv --subtitle /tmp/test.srt
subsyncd forget-instance --config /config/config.yaml --instance sonarr-old
subsyncd forget-instance --config /config/config.yaml --instance sonarr-old --yes
subsyncd webhook-url --config /config/config.yaml --instance sonarr-main
subsyncd webhook-url --config /config/config.yaml --instance sonarr-main --base http://subsyncd:8097
subsyncd rotate-webhook-token --config /config/config.yaml --instance sonarr-main
subsyncd --version
```

Exit status is 0 for success, 1 for an operational failure, and 2 for invalid command usage. `serve`, `scan`, `search`, `reject`, `retry`, `rotate-webhook-token`, and `forget-instance --yes` take the nonblocking `/data/subsyncd.lock` before migrations or durable initialization and retain it until application close (`scan`, `search`, `reject` and `retry` do so only without a running daemon, which otherwise carries them out); a second mutator fails before changing startup state with code `busy`: a stop-first command's message says to stop the daemon first, a routed command's that another process (a daemon still starting, or another command) holds the lock and to try again shortly. Stop the daemon before running `rotate-webhook-token` or `forget-instance --yes`. `scan`, `search`, `reject` and `retry` are routed.

A running daemon also serves a control socket, `<data_dir>/subsyncd.sock` (mode 0600, removed on shutdown, a stale file replaced at start because the lock is held). A Unix socket path is limited to about 104 bytes on macOS and 108 on Linux (`sun_path`), so a very long `data_dir` makes the listen fail; tests use short temporary directories for this reason. Each connection carries one version-1 JSON request (at most 64 KiB) and one response; see `internal/control`. `serve` starts it after the lock is held, as one more component in the shutdown sequence: it stops with the run context, drains in-flight requests inside the existing shutdown budget, and answers `daemon_stopping` meanwhile. The drain waits at most 30 seconds (`Server.DrainTimeout`, like the manual-search drain); a handler still running then, blocked in I/O it cannot interrupt, is left behind with its connection closed. Readiness and startup do not depend on it, but a failure to listen on or accept from the socket is a component failure like the HTTP server's and ends `serve` with an error. `App.HandleControl` decodes arguments strictly (unknown fields or an unknown command are `usage` errors) and reuses the `App` method; because the daemon holds the lock, that method takes the no-op lock path. Without a daemon socket, the routed methods take the lock before checking `--timeout`/`--no-wait`, so a daemon still starting (lock held, socket not yet listening) reads as `busy`, with a message that names that case rather than the stop-first advice (`App.acquireRoutedLock`; `Options.Command` chooses the message when `New` takes the lock). `retry` then signals the worker's wake channel without blocking. The CLI (`cli.Command.Dial`, wired in `cmd/subsyncd`) dials the socket for routed commands (`retry`, `search`, `reject` and `scan`) after loading the configuration for `data_dir`; `control.ErrNoDaemon` (no socket, or nothing accepting on it) or an unloadable configuration falls back to opening the backend as before, and any other dial error is reported. Each request logs `control.request_completed` or `control.request_failed`.

A daemon `scan` (`App.scanInDaemon`) waits like a manual search (`daemonWait`: default 5 minutes, none with `--no-wait`, `running` when the wait ends first) but runs on the daemon's run context, so a vanished client or a request timeout never cancels it. It runs inside the reconcile fence: `Worker.WithReconcileLock` takes `reconcileMu`, the mutex `reconcileDueContexts` holds for each scheduled reconciliation, so a scan and a scheduled reconcile (including its discovery and cursor handling) never overlap and neither observes the other's half-applied snapshot; two scans serialize on the same fence. The wait for the fence honors the context, and an abandoned wait hands the lock back. The worker's own due-reconcile path uses `TryLock` and skips reconciliation for that tick when a scan holds the fence, so a running scan never delays search leasing or notification delivery; the skipped reconciliation is retried at the next tick. Only discovery and history reconciliation run inside the fence: the `--force-probe` loop runs after it, and a file replaced or deleted since the listing (`store.ErrStaleInventory`) is skipped and counted in `probe_skipped` (text `probe_skipped=N` only when above 0) instead of aborting the scan; other errors still fail it. Every daemon scan logs `scan.completed` or `scan.failed`, since the request may have stopped waiting before it ended. `App` finds the fence by type assertion on its worker (`reconcileFence`); when the worker has none, the scan runs directly. Scans count in `manualRuns`, so shutdown cancels them through the run context and waits for them inside the existing manual drain window, adding no new one; a waiting request then answers `daemon_stopping`. Without a daemon, `App.Scan` takes the data-directory lock and runs to completion, and `--timeout`/`--no-wait` fail with `daemon_required`.

`explain`, `find`, `doctor`, `analyze-sync`, `webhook-url`, and `forget-instance` without `--yes` (opened as `forget-instance-preview`) open an existing current-schema database read-only and can run while the daemon holds its lock. They do not apply migrations, add configured-language searches, or create persistent caches. A missing or outdated database requires initialization by a mutating command first. Diagnostic LAPSE analysis uses temporary cache storage. Startup failures already emitted as structured events are not printed again as raw CLI errors.

`forget-instance` refuses an instance that is still configured and fails with an unknown-instance error when neither an `instances` row nor any `media` row names it. Without `--yes` it opens read-only and counts rows in a transaction it rolls back. With `--yes` it first confirms `PRAGMA foreign_keys` is on (every media child but `events` is removed by cascade) and then one transaction deletes the instance's outbox notifications (matched on `payload.media.ref.instance`), its audit events (by `instance` or owned `media_id`, before the media rows so `ON DELETE SET NULL` cannot orphan them), its reconciliation replays, its search history (`search_history` by `instance`, which would otherwise keep the name, file ID and title for 30 days), its waiting webhooks (`webhook_inbox`) and the pending-install records of its media (so the startup sweep never undoes a file it no longer tracks; neither is counted), its media rows (cascading to tracks, probes, hashes, searches, candidates, rejections, LAPSE failures and installations), and finally the `instances` row. Provider state and the provider and pack caches are not keyed by instance and are kept. Subtitle files are never touched; they become unmanaged sidecars. Hidden `.subsyncd-rollback-*` copies named by `installations.rollback_path` also stay and lose their only record, so the output reports them as `rollback_copies`. Migration `018_media_child_indexes.sql` adds `candidates_media_idx` and `events_media_idx`; without them every deleted media row made the candidates cascade and the events `SET NULL` action scan the whole table. Like every migration, 018 can't be rolled back. Success logs `instance.forgotten` with the instance name and per-table `*_count` fields.

`explain` reports the indexed media identity, embedded/sidecar tracks, human-readable search priority, pending-rerun state, missing/failure attempts, last outcome and next attempt, candidates with score/identity evidence, retained candidate rejections with reason and `expires=never`, managed installation and LAPSE provenance, reusable pack count, and provider cooldowns. `search --retry-rejected` clears subsyncd's own rejection records (and LAPSE strikes) for only the selected media/language before performing the manual search; any candidate that deterministically fails again is immediately re-quarantined. The owner's rejections (`user_*`, from `reject`) are kept; only `reject --undo` removes them.

Media selection is shared by `find`, `explain` and `search` (`control.Selection`; `App.Resolve` and `App.Find` in `internal/app/find.go`). Exactly one of `--file-id` (with `--instance` and `--kind`), `--title` or `--path` is allowed; `--instance` and `--kind` narrow the other two. `--title` is parsed by `selection.ParseTitle` and matched by `Repository.MatchMedia`: SQL narrows by instance, kind, year and season/episode (a file whose range covers the episode matches), then titles and alternate titles are normalized in Go (`selection.Normalize`: lowercase, a built-in fold table for Latin-1 and Latin Extended-A, apostrophes and periods dropped, other punctuation a space) because SQLite's `lower()` folds ASCII only. An exact normalized title ranks before a substring and only the best rank is returned; deleted media never matches. `--path` is compared exactly with `media.path`, both as given (cleaned) and after `catalog.MapPath` through each configured instance's mappings (only `--instance` when set). `Resolve` returns exactly one file or a coded `media_not_found` / `ambiguous_media` error (the latter lists at most 25 candidates in `Candidates`); `find` never fails on several matches. Language state for `find` comes from `Repository.LanguageStates` with the precedence running (a live search lease), installed (an installation row), satisfied (last search outcome `satisfied`), then missing. `search` with `--title` or `--path` resolves only indexed media and then follows the `--file-id` path, including the Arr lookup (a connection failure or timeout there is `arr_unreachable`, via `catalog.ArrUnreachable`); `--file-id` alone still indexes an unknown file. Without `--language`, `search` takes the configured languages absent from `LanguageStates` (missing); when none is, nothing runs and each language reports `satisfied` (or `running` for a live lease).

### Manual search lease

Every manual search, in the daemon and in-process alike, goes through `App.runManualSearch` (`internal/app/manual_search.go`), so the worker can never run the same media and language beside it. It first takes one of two manual slots (`manualSlots`, a FIFO semaphore separate from `worker.max_concurrent`; a waiter whose context ends leaves the queue holding nothing). It then claims the search's lease with `Repository.ClaimSearch` under a fresh `manual-<hex>` owner: one upsert that creates a missing `search_states` row as a pending missing-priority search and otherwise sets `lease_owner`/`lease_until_ns` only when the row is unleased or its lease expired (clearing a dead owner's `rerun_requested`, like `LeaseDueSearchesExcept`). While another owner holds a live lease (normally the worker running that search) the claim reports false and is retried every second, so the manual search waits for the worker to finish and runs afterwards with full manual semantics; it never sets `rerun_requested`, which would only queue an ordinary search the CLI could not wait on. Holding the lease, it renews it every third of its 5-minute duration (`RenewSearchLease`; a failed renewal cancels the run, which then fails), clears provider-resume progress, clears subsyncd's own rejections for `--retry-rejected`, and runs the workflow with `Manual: true` under the worker's job time limit and abandonment rule: past `2 × max(sync.max_timeout, sync.timeout)` the workflow's context is canceled, and one that has not returned `worker.JobGrace` (2 minutes) later is abandoned with its canceled context, so a call that ignores cancellation cannot hold a manual slot or the lease forever. A timed-out run logs `job.timed_out` and, while it still owns the lease, completes the search as a technical failure on the failure schedule (`workflow_error`, like the worker), so the worker does not lease it again at once beside the stuck workflow. Once the workflow has returned a result, the bookkeeping below (completion, settle, release, upgrade schedule, history row) runs under `context.WithoutCancel`, so a shutdown right after an install still records it. An `installed` outcome completes the search under the manual lease with `CompleteSearch`, as the worker completes an install (`App.completeManualInstall`): the new subtitle's `NextUpgrade` with upgrade priority (or `complete` when there is none, a preferred exact hash), the missing/unchanged-check and failure counters reset, and the lease released in the same owner-guarded update; a rerun requested during the claim keeps the search pending as for any completion. The queued search's due time and counters described the subtitle the run replaced, or a missing one, so keeping them would carry a fallback's unchanged-check count (exempt from `upgrade_checks`) over to a preferred promotion and stop its checks early. For any other outcome, when the search row did not exist before the claim (`ClaimSearch` created it) or the search just added or revived the media, a `satisfied` outcome settles that pending search with `SettlePendingSearch` under the manual owner, which leaves it pending when a change arrived during the claim and requested a rerun. Otherwise a search queued earlier is not settled by a manual run: its class, due time and missing or unchanged-check counters stay as they were, and `EnsureUpgradeSearch` can only bring its due time forward. The lease is then released (`ReleaseSearchLease`) and, because `EnsureUpgradeSearch` changes only unleased rows, the upgrade schedule is kept afterwards; a worker that leases the search in that gap schedules its own. Every other path (claim failure, workflow error, cancellation) releases the lease from a deferred call with a fresh context bounded to 5 seconds, so a canceled run still gives the search back; releasing a lease no longer held does nothing. A manual search logs `job.started` and `job.completed` (`component=app`, `priority=manual`, the manual `job_id`; `outcome` is the workflow outcome, `failed` or `canceled`).

In the daemon, `search` resolves and indexes the media on the request, then starts one `runManualSearch` per language on `serve`'s run context, never the request's, so a client that disconnects cancels nothing. The handler waits for all of them or for `SearchArgs.Wait`, whichever comes first (5 minutes when 0; not at all with `NoWait`), and reports `running` for each language not finished; a language that failed fails the request. The CLI sends `Wait` only for `--timeout` and `NoWait` for `--no-wait`; the in-process `Search` refuses either with `daemon_required`. On shutdown the run context is canceled together with the worker's, the waiting handler answers `daemon_stopping`, and after the control server has drained its requests `serve` waits up to 30 seconds (inside the worker's drain windows, so no new window) for the canceled searches to release their leases.

### Replaced and renamed media files

The media row follows the stable Arr entity, so an upgrade, a re-import or a replacement in place reaches the same row with another Arr file ID or size. Installations record the file they were installed for: `media_path`, `media_file_id` and `media_size` (with `media_mod_time_ns`). When the content changes (`upsertMediaTx`, `UpsertMedia`, `ReplaceTrackInventory`), `invalidateInstallationTx` clears only the scoring and synchronization evidence, `fallback` and `media_mod_time_ns`; the file identity stays, so the workflow can tell a replaced file from the same file with a new modification time. Only a rename of the same file (same Arr file ID and size, new path) renames sidecar records, record-only (`rebaseInstallationPathsTx`, for installations of that file or of unknown provenance), and it leaves `media_path` at the old media path until the workflow has checked the sidecar. A replaced file's records keep their old sidecar path. (Before this, every path change renamed the records, also for an upgrade to a differently named release, while the files stayed where they were: a record could name a file that did not exist, or another release's subtitle with the checksum of the one installed for the replaced file, which then looked like the owner's edit forever.)

`Service.Run` settles the language's installation before the inventory decides anything: `Installer.ReconcileInstallation` (`internal/workflow/installation_reconcile.go`) compares the record with the live media fingerprint. A record whose Arr file ID changed but whose recorded size is known (non-zero) and unchanged is the same file when its media path is unchanged or its unchanged sidecar is named after the current media file (at the recorded path, or there after Arr renamed it): `Repository.ReattachInstallation` (guarded by the record as read, including the old file ID and size) sets `media_file_id` and the sidecar path, `install.reattached` is logged, and it is settled as the same file below. This covers a re-import of identical bytes or an Arr database restore. A rename of the same file is checked on disk: the sidecar at the new name with the recorded checksum (Arr moved it) sets `media_path` to the new media path (`Repository.RebaseInstallation`, guarded by the record as read) and removes a hard link of it left at the old name; one Arr left at the old name is hard-linked to the new name (never over an existing file; where hard links fail, renamed with `renameat2(RENAME_NOREPLACE)` on Linux or `renamex_np(RENAME_EXCL)` on macOS, never with a check-then-rename), recorded there, and unlinked from the old name; one that exists nowhere drops the record. When the link fails with `EXDEV` (the new name is on another filesystem), or the fallback rename is unsupported (`EINVAL`/`ENOSYS`/`EOPNOTSUPP`, or no such call on the platform), the record is dropped with reason `sidecar_unmovable` and the file left at the old name, so the search runs instead of failing on every pass. The move is covered by a `pending_installs` row (`destination` the new name, `rollback_path` the old one, `staged_path` empty, `published_inode` the old name's inode) from before the link until the old name is unlinked: a crash before the commit is finished by the next pass (the record already names the new path), and a crash or a failed unlink (`install.rename_cleanup_failed`) after it by `RecoverPendingInstalls` at the next start, which unlinks the old name only while it is a regular file with that inode and the recorded checksum and a second name of the file at the new name. `removeSameFile` unlinks a name only as a second link of the file at the other name: the names differ byte for byte, the file has at least two links, and both names are listed as spelled in their directory (names in different directories always are). A case-only rename on a case-sensitive filesystem therefore loses its old spelling like any rename; on a case-insensitive filesystem both spellings name one directory entry (link count 1, or only one spelling listed when the file has another link elsewhere), so nothing is unlinked, the rename is treated as already moved, and recovery reports `move_cleaned`. When another file holds the new name, the left-behind managed sidecar is removed through `RemoveManaged`. For the same file under the same path, a vanished sidecar drops the record, and a changed one not named after the media file does too; a changed one named after it stays as the owner's edit. For a replaced file (another size, or another file ID not reattached above), or a record whose file identity an older build cleared (`media_file_id=0`), the old sidecar at its recorded path, or at that path renamed after the new media file (Arr carried it over), is removed through `RemoveManaged` with reason `media_replaced` when it is a regular file in the media folder with the recorded checksum. These deletions are capped at `workflow.MaxReplacedRemovalsPerHour` (20) per rolling hour per process (`Installer.ReplacedRemovals`, an in-memory `RemovalBudget` that `app.New` creates; a restart starts a new window): past the cap nothing changes (the sidecar and the invalidated record stay, `install.removal_deferred` is logged at warn with `reason=cap` and `retry_at`) and the `Reconciliation` is `Deferred`, with `RetryAt` when the window's oldest deletion leaves it (`RemovalBudget.nextSlot`) plus `removalRetryMargin` (1 minute). `Run` then searches nothing and returns `OutcomeThrottled` with that `RetryAt` and `Result.RemovalDeferred` (reason `removal_deferred` in `search.completed` and `job.completed`), so the worker completes it like a provider throttle: queue order kept, attempts not advanced, `replace_installed` kept. Installing instead would record the new file's subtitle over the old record (it is one row per media and language) and leave the old sidecar untracked for good when the new file has another name. The retry deletes the sidecar first, if it is still there and the record unchanged, then searches. A reservation is given back when the removal does not happen; otherwise (missing, edited, a symlink, elsewhere) only the record is dropped and the file stays, now an unmanaged sidecar. The one exception keeps today's behavior: a record of unknown provenance whose unchanged sidecar has the current media file's name stays managed. Dropping (`Repository.DropInstallation`) is a guarded delete with a `subtitle_record_dropped` audit event whose outcome is the reason (`media_replaced`, `sidecar_missing`, `sidecar_changed`); it touches no sidecar and deletes the record's rollback copy. `ReconcileInstallation` returns a `Reconciliation` (`Changed`, `Removed`, `Deferred` with `RetryAt`). When anything changed, `Run` refreshes the inventory and rereads the installation, and the search goes on for the current file as for a missing subtitle; when the sidecar was removed during a `ReplaceInstalled` (reject) run, a search that ends `no_result`, `rejected` or `satisfied` reports `removed` with that outcome in `RemovedAfter`, like `removeRejected`, and its history row is the removal's; the import or rename already queued that search at import priority (a replacement in place queues it for installed languages). Events: `install.removed` with `reason`, `install.record_dropped`, `install.renamed`.

### Reject, replacement and removal

`reject` (`internal/app/reject.go`) resolves the media like `search` and picks the language: `--language`, or the only one with an `installations` row (several are `usage`, none `not_managed`). `prepareReject` changes nothing: the installation must exist, lie inside a media root, and be a regular file whose SHA-256 still equals `installations.checksum`; otherwise `not_managed`. An invalid or missing `--reason` is `usage`.

The durable step, `Repository.RecordUserRejection`, is one transaction: it upserts a `candidate_rejections` row with reason `user_<reason>`, the installation's `candidate_signature` (or `*` when empty, from before migration 023) and `artifact_checksum`, the current media fingerprint (from the resolved media row, so a media file replaced since the install, whose installation provenance is invalidated, still gets a valid rejection) and the current tool signature; and it sets the `search_states` row to pending, due now, import priority, attempts reset, resume progress cleared, `replace_installed=1`. The same statement leases the row to the reject's `manual-<hex>` owner when it is unleased, so the worker cannot take it before the manual run; a row another owner holds gets `rerun_requested=1` instead, so that owner's completion leaves it pending. `ClaimSearch` accepts a claim by the lease's current owner, which is how the manual run then claims it. If the process stops before the manual run finishes, the rejection and the queued replacement stay; the manual lease expires after five minutes and the worker takes the search with `SearchLease.ReplaceInstalled`.

`runManualSearch` reads `replace_installed` after claiming (a run that finished the replacement meanwhile has cleared it) and passes it as `workflow.Request.ReplaceInstalled`; the worker passes the leased value. With it, `Service.Run` treats a managed installation that is still present and unedited as not installed, whether or not its provenance still matches the media file (a new modification time alone invalidates it, and the sidecar is still subsyncd's; a replaced file's sidecar is removed before, see [Replaced and renamed media files](#replaced-and-renamed-media-files)): no exact-hash satisfied shortcut, no `ShouldUpgrade`, no same-candidate reassessment, the fallback tier allowed. The best acceptable non-rejected candidate is installed over it at its path through the normal `Installer.Install` (rollback copy, pending row, provenance and notification transaction). A format-changing candidate and one whose prepared text has the rejected checksum are skipped for that run. When the inventory is already satisfied by another track (embedded or an unmanaged sidecar), the workflow removes the rejected sidecar without searching (`RemovedAfter=satisfied`). When the finished search's outcome is `no_result` or `rejected` and no provider on the route reported a technical error (`Result.ProviderErrors` empty), the workflow calls `Installer.RemoveManaged` and returns `OutcomeRemoved` (`Result.RemovedAfter` keeps the search outcome, reported as the result's `reason`). A throttled search, any error, or a provider error beside an otherwise empty search (returned as a technical failure) keeps the subtitle and leaves `replace_installed=1` for the retry. An edited, deleted or replaced sidecar is not managed any more, so it is neither replaced nor removed.

`Installer.RemoveManaged` (`internal/workflow/remove.go`), used by `reject` and for a replaced file's sidecar (see above), checks containment (`containedDestination`) and the checksum (`ErrManagedSubtitleChanged` otherwise, which `reject` and the workflow treat as the owner's file: nothing changes). It records a `pending_installs` row whose `rollback_path` is a hidden `.subsyncd-removing-<hex>` name in the subtitle's directory and whose `staged_path` is the installation's old rollback copy, renames the subtitle to the hidden name, re-checks its checksum (an edit in between restores it), fsyncs the directory, and commits `Repository.RemoveInstallation`: the guarded delete of the `installations` row (path, checksum, provider, candidate and rollback path must still match), a `subtitle_removed` audit event, a `search_history` row with outcome `removed` (reason `media_replaced` or `media_renamed` for a media change, empty for a reject), and one notification intent per notifier with a removal-specific dedupe key (the Silo payload names the same folder). A failed commit links the subtitle back (never over a recreated destination) and clears the pending row. After the commit it logs `install.removed`, then deletes the hidden file and any rollback copy still recorded (the superseded older subtitle is deleted, not restored) and clears the pending row. `RecoverPendingInstalls` recognizes a sidecar move (`isPendingMove`: empty `staged_path`, a `rollback_path` without a `.subsyncd-` prefix; see above) and the removal prefix: while the installation row still matches, the removal did not commit and the subtitle is linked back (unless the destination was recreated); once the row is gone the hidden file and the old rollback copy are deleted.

A replacement run completes its search like a worker completion and clears `replace_installed` in the same owner-guarded `CompleteSearch` (`SearchCompletion.ClearReplaceInstalled`, ignored while a rerun is requested): installed or satisfied schedules the upgrade, removed (and no_result or rejected) the missing-subtitle schedule, throttled keeps the flag and waits for the reset. A removed completion writes no history row; `RemoveManaged` wrote it. `reject --undo` calls `ClearUserRejections` for the file and language, which in the same transaction clears `replace_installed`, and runs no search. A run already under way read the flag when it started and finishes; no completion sets the flag again.

## Silo notification

Enable Silo only after setting its native API URL and admin API key:

```yaml
silo:
  enabled: true
  url: http://silo:8080
  api_key: 'your-silo-admin-api-key'
  path_mappings:
    - from: /media
      to: /mnt/media
```

The installation provenance and one checksum-deduplicated intent per configured notifier are written in the same SQLite transaction as the filesystem publication's logical commit. Deduplication applies while an intent is pending: completing it with a terminal result (delivered or rejected) clears its `dedupe_key`, so a later publication of the same subtitle enqueues a new scan. Migration `016_release_finished_notification_keys.sql` clears the keys of notifications that finished before this change. If that durable database operation fails, the new sidecar is removed or the prior managed copy is restored. Only after it commits does asynchronous delivery send `POST /api/v2/scan` with `Authorization: Bearer …` and the mapped parent directory of the media file. Intents leased in the same batch whose notifier reports the same coalesce key (`notifier.Coalescer`; Silo uses the mapped scan directory) share one delivery, and each is completed with its result. A later Silo failure never rolls back the subtitle or installation; timeout, 408, 429, and 5xx responses retry independently, while other 4xx responses are terminal. See [the Silo API reference](../references/silo.md).

This adapter requires Silo API v2 and has no v1 compatibility or version fallback. Keep `silo.url` set to the server base URL, without an API suffix. Silo marks scan dispatch as non-idempotent: the durable outbox provides at-least-once notification delivery, so an uncertain transport failure or lease recovery can repeat a targeted scan. There is no immediate HTTP retry or cross-version replay. Existing pending intents use v2 after upgrading; completed intents are not replayed.

## Arr rescan notification

After each committed install, removal or move of a managed sidecar, the owning Arr instance is asked to rescan the series or movie, so Sonarr and Radarr learn about it before their scheduled refresh (Sonarr 12 hours, Radarr 24). It uses the same outbox as Silo: notifier name `arr_rescan` (`notifier.ArrRescanName`) in `notifications.notifier`, the same `workflow.NotificationPayload`, leasing, coalescing and backoff. No migration was needed: `notifier` is free text, and the payload's media already carries `ref.instance`, `ref.kind`, `series_id` (Sonarr series) and `entity_id` (Radarr movie). Pending Silo intents are untouched.

`Installer.changeNotifierNames` (`internal/workflow/notification.go`) adds `arr_rescan` to the configured notifiers when the media's instance is in `Installer.ArrRescanInstances` (instances whose `rescan_after_changes` is not `false` and that have a rescan client) and `notifier.RescanID` knows the ID (an episode's `series_id`, a movie's `entity_id`); without the ID it logs `notification.skipped` (`reason=unknown_arr_id`) and queues the others. It is used by `Install` (new, replacement, upgrade, promotion and manual installs), `RemoveManaged` (reject removal and a replaced file's sidecar, `media_replaced`/`media_renamed`) and `moveRenamedSidecar` (a sidecar Arr left behind on a rename), which queues only `arr_rescan`, in the same transaction as the record (`Repository.RebaseInstallationWithNotifications`); Silo was never told about moves. A same-bytes provenance refresh (`refreshIdenticalInstallation`) and a reattached record touch no file and queue no rescan. Three disk changes queue none either: `RecoverPendingInstalls` undoing an install a crash interrupted, `followRename` unlinking a hard link left at the old name after Arr moved the sidecar itself (Arr already knows the new name), and `RecoverPendingInstalls` unlinking the old name of a move whose commit already queued the rescan. Silo dedupe keys follow the install and removal rules (a move would use a `moved` key). An `arr_rescan` intent with a known ID instead has a key naming its target, the hash of `arr_rescan` and `notifier.RescanCoalesceKey` (instance, kind, series or movie ID), and `NotificationRequest.Coalesce` (`workflow.notificationRequest`). `enqueueNotification`, in the transaction of the change, then looks the key up: an unleased row with it (pending, or retry-scheduled after a failed delivery) absorbs the change, inserting nothing and keeping its due time, so a steady trickle of changes cannot postpone the rescan; a leased row, which may already have been sent, gives its key up (`dedupe_key=NULL`) and a new row is inserted, so the later change is rescanned too. Should that in-flight delivery then fail and retry, both rows are delivered (one extra rescan). Rows queued with per-change keys by an older build are not absorbed and are delivered as before.

`notifier.ArrRescan` also coalesces on (instance, kind, series or movie ID) within one leased batch. An `arr_rescan` intent is first due `notifier.ArrRescanDelay` (60 seconds) after the change that queued it (`notificationDue`; Silo intents stay due at once and lease first, ordered by due time); changes until it is leased join it (see above), so a series is rescanned at most about once per delay while changes keep coming. Rows of one target leased in one batch (older per-change rows, or more than a batch, `NotificationBatch`, 10 per maintenance tick) share one command. It sends `POST /api/v3/command` with `{"name":"RescanSeries","seriesId":<id>}` (Sonarr) or `{"name":"RescanMovie","movieId":<id>}` (Radarr) through `catalog.ArrRescanClient`, which uses the Arr client's bounded JSON write (`sendJSON`: `X-Api-Key`, 1 MiB request limit, no redirects, error bodies discarded except validation property names) with its 15-second timeout. Never `RefreshSeries`/`RefreshMovie`, which query metadata providers. Any 2xx (Arr answers 201) is delivered. No answer, a timeout, 408, 429 and 5xx are retryable with the usual `schedule.FailureDelay` backoff. Any other status (404 for a deleted series, 400, 401) is `DeliveryError.Refused`: completed with result `refused` and logged as `notification.abandoned` (warn), never retried. An intent for an instance whose rescans were turned off or which was removed since it was queued, or whose ID is unknown, completes as `skipped` (`notifier.SkippedError`) without a request. `app.New` registers the `arr_rescan` notifier even when no instance rescans (an empty map), so intents left from before rescans were turned off, or from a newer build, complete as skipped (`rescan_disabled`) rather than failing as an unconfigured notifier. `app.New` builds the clients from each instance's `url` and `api_key`; `Options.ArrRescanners` replaces them in tests, and tests that supply `Options.Catalogs` without it get none, so they make no Arr requests.

## Backup, restart, and recovery

For a consistent backup, stop the service and copy `/data` as one unit. It contains the SQLite database and both caches. Restoring only the database can leave pack manifests missing; those entries are detected and invalidated safely, but the cache benefit is lost.

Search and notification leases are recoverable after five minutes. A job that returns because of shutdown gives its lease back (`ReleaseSearchLease`, `ReleaseNotificationLease`, best effort within 5 seconds), so the next start leases it at once; an undelivered notification group releases every member. An expired lease counts as no lease: claiming it clears a rerun the dead owner left requested (the new job reads current state anyway), and `retry --provider`, a manual search's claim and its settlement treat it as unleased. On shutdown, workers receive one graceful drain window, then cancellation, then one final equally bounded window. The Compose example allows 75 seconds before forced termination, covering both default 30-second windows with exit margin. The window length is fixed in code (`Worker.ShutdownTimeout`) and is not configurable; raise the Compose grace period if that default changes. A cancellation-insensitive external operation may outlive the daemon return, but its lease is deliberately not cleared and becomes recoverable after expiry; operators should avoid starting a replacement process against the same media mounts until the old process/container has actually stopped.

Search claims include only configured instance/language routes and active media. Removing a route preserves its stored work without retrying it; re-enabling the route makes eligible work claimable again. `forget-instance` is the only way to discard a removed instance's records. Deleting media retains any active lease until its owner completes. Reimport during that lease requests one rerun instead of overlapping the existing workflow.

A crash after atomic publication but before search completion does not trigger a second installation: the next inventory pass recognizes the checksum-recorded sidecar. A crash between publication and recording the installation is settled at the next start. Before publishing, the installer records a `pending_installs` row (migration 020) with the destination, checksum, staging and rollback paths, and the inode of the staged file (`published_inode`, migration 021), which linking and renaming keep; recording the installation (in the same transaction, `Installation.PendingInstallID`), or a complete rollback, clears it. Only a mutable start (`serve` and the mutating commands), after it holds the mutation lock and before the worker exists, settles each row left behind (`Installer.RecoverPendingInstalls`); read-only diagnostics (`explain`, `doctor`, `analyze-sync`, the `forget-instance` preview) never do, since without the lock a row may be the daemon's install in progress. The sweep waits at most 30 seconds: one stuck on a hung mount is abandoned with `install.recovery_timed_out` (warn), startup continues, and its rows are kept for the next start. It settles only the rows listed when it began, its context is canceled when abandoned, and it checks the context before each filesystem change, so once its blocked call returns it changes nothing more. The residual risk is the one call already in flight: if that is the undo itself, it lands late. It arises only on a hung mount, where the daemon's own installs to that mount fail too, and the undo still applies only while the destination is that row's publication (same inode and checksum). Recovery settles each row: an installation recorded with that checksum keeps its subtitle and rollback copy (the sweep below deletes the copy); otherwise, if the destination is still the published file (same inode and checksum; rows without an inode compare the checksum alone), the previous managed subtitle is restored from the rollback copy, or the unrecorded subtitle is removed, so it does not linger as an untracked sidecar that blocks every future install. The device number is not compared at startup, because it can change across a restart (device-mapper, network and overlay mounts) while the destination path already fixes the filesystem. A destination that cannot be inspected or read fails that row (`install.recovery_failed`) and leaves it for the next start, since undoing blind could overwrite a newer install. Staging files and unused rollback copies are removed, and `install.recovered` reports `outcome` `recorded`, `undone` or `cleaned`. The search itself is retried when its lease expires. A managed replacement keeps its rollback copy only until the installation is recorded: a database-commit failure restores it immediately, and once `RecordInstallationWithNotifications` has committed, `Installer.discardRollback` deletes it (a regular file named `.subsyncd-rollback-*` in the subtitle's folder) and clears `installations.rollback_path`. A failed deletion logs `install.rollback_cleanup_failed` (warn) and never fails the install; the copy stays recorded for the startup sweep, as does one a crash left between the commit and the deletion (recovery keeps a recorded install's copy, as before). Nothing restores a copy after the commit (`reject` and `--undo` do not use it). Right after `RecoverPendingInstalls`, under the same 30-second bound and only in a mutable start, `Installer.DiscardRollbackCopies` deletes every copy still recorded, including those older builds kept until the next replacement: for each installation with `rollback_path<>''` and no `pending_installs` row, it deletes the copy only when the sidecar is a regular file at its recorded path inside a media root and the copy is a regular file named `.subsyncd-rollback-*` directly in that folder, then clears `rollback_path`; a copy already gone is only forgotten, anything else is skipped. It checks the context before each filesystem and database change, so an abandoned sweep (`install.rollback_sweep_timed_out`, warn) changes nothing more, and running it again is harmless. `install.rollback_sweep_completed` (info) reports `removed_count` and `skipped_count` when there was anything to do; `install.rollback_sweep_failed` (warn) a sweep that stopped on an error. Before rolling back, the installer checks that the destination is still the file this run published, by identity (`os.SameFile` against the staged file), not content: a run abandoned while publishing can fail its database write long after another run published a subtitle, possibly with the same text, which is then kept, and only this run's rollback copy is removed (`install.rollback_skipped`, warn). A replacement is also not rolled back when another run has recorded an installation for that media and language since this run began, because this run's rename may have landed after that run's install, and its rollback copy is older than both. When the answer is unknown, the safer side is taken per case. A first install whose destination cannot be inspected is still treated as this run's and removal is attempted: no other run publishes over a sidecar it has not recorded, and keeping it would leave an untracked subtitle. A replacement whose destination cannot be inspected, or whose installation record cannot be read, is not restored, since that could overwrite a newer install; the destination, the rollback copy and the `pending_installs` row are kept for the startup sweep. If removal of a newly published sidecar or restoration/fsync of a replacement also fails, the combined technical error is logged and returned. The destination or rollback copy is retained rather than silently discarded. Such a sidecar may be valid but untracked and is therefore protected from automatic takeover; inspect it and `explain` before resolving it manually.

A removal (`reject` with no acceptable replacement) uses the same `pending_installs` table with a `.subsyncd-removing-` rollback path; the startup sweep restores or deletes it as described under [Reject, replacement and removal](#reject-replacement-and-removal).

If a user wants to take ownership of a subtitle, edit or replace the sidecar. Its checksum then differs from provenance and `subsyncd` protects it. Use `explain` before removing any generated file; never delete arbitrary `.subsyncd-*` files while the daemon is running.

## Troubleshooting

- `another subsyncd mutation process is active`: stop the daemon or wait for the other one-shot mutator; do not delete the lock file to bypass a live lock.
- `media path is outside configured roots`: fix the Arr path mapping or mount path; do not broaden roots merely to silence the check.
- no provider call: check `explain` for an embedded/protected track, exact terminal installation, future schedule, pack cache, or provider cooldown.
- repeated missing result: this is expected backoff, not a worker sleep. Use `search` for a deliberate manual attempt or `retry` only to clear provider throttle/auth state.
- LAPSE rejection: inspect `candidate_rejections` with `explain`; `unsure`/`nothing` is intentionally not installable. Use `analyze-sync` for diagnosis or `search --retry-rejected` after changing the media, candidate source, LAPSE build, or policy.
- Silo does not refresh: confirm the configured port reaches Silo's native API, the key is an admin API key, and the container-to-Silo path mapping is correct.

## Minimal FFprobe packaging

The image builds static FFprobe 8.1 from a checksummed FFmpeg source archive using a digest-pinned Alpine builder. Only local-file protocols and the container/parser/subtitle capabilities needed for inventory are enabled. The full `ffmpeg` command is not installed. LAPSE v2.2.4 retains its own linked FFmpeg libraries, ONNX Runtime and Silero model; `libstdc++6` remains an explicit runtime dependency.

`scripts/build-ffprobe.sh` verifies the source digest and target architecture, builds the probe, and emits its license and a CycloneDX source-component inventory under `/usr/share/sbom/ffmpeg.cdx.json`. Both Dockerfiles run FFprobe version and LAPSE/Silero load checks during the image build, including both platforms built by GitHub Actions. Keep the version, source hash and runtime version label synchronized when upgrading.
